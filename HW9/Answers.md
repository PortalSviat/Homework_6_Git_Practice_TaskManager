# ДЗ 9. Интерфейсы

## 1.1

### 1

`List<IDamageable>` позволяет передать в метод и игроков, и ловушки в одном списке. Для метода важно только то, что объект умеет получать урон. При вызове `TakeDamage` у игрока уменьшится здоровье, а у ловушки выполнится её собственный метод. Это полиморфизм: вызов общий, а поведение зависит от конкретного объекта. Новый класс с этим интерфейсом тоже можно будет обрабатывать без изменения `ProcessDamage`.

### 2

Формально ловушка реализует интерфейс: все нужные методы и свойства есть. В самом интерфейсе не написано, что именно означает `false`, поэтому компилятор не считает такую реализацию ошибкой. Но по смыслу поведение странное: ловушка разбилась, а здоровье осталось 10. Если другой код проверит её HP, он может решить, что она ещё целая. Поэтому после разрушения лучше сохранять HP равным нулю, а не всегда возвращать 10.

### 3

`HealthPotion` не реализует `IDamageable`, поэтому добавить его в `List<IDamageable>` нельзя. При обычной попытке это будет ошибка компиляции. Если обойти проверку через `object` и явно привести объект зелья к `IDamageable`, получится `InvalidCastException` при выполнении. Даже такой обход не дал бы лечения, потому что `ProcessDamage` вызывает `TakeDamage`, а не `Heal`. Для лечения нужен отдельный метод, работающий с `IHealable`.

### 4

Изменить нужно `Player` и `Trap`, потому что они реализуют `IDamageable`. В них придётся добавить свойство `IsDead`, иначе проект не скомпилируется. У игрока можно проверять `HP <= 0`. Для ловушки нужно хранить состояние разрушения, так как сейчас её HP постоянно равно 10. `HealthPotion` и `GameSystem` из-за добавления этого свойства менять не обязательно: они сами этот интерфейс не реализуют.

## 1.2

В таблице учитываются возможности C# 8 и новее. Под конструктором имеется в виду конструктор объекта.

| Утверждение | Abstract class | Interface | Комментарий |
|---|:---:|:---:|---|
| Может содержать поля с конкретными значениями | + | +* | Абстрактный класс может хранить состояние отдельных объектов. В современном интерфейсе допустимы статические поля с начальными значениями, но поля экземпляра запрещены. |
| Может иметь полноценный конструктор | + | − | Конструктор абстрактного класса вызывается при создании наследника. У интерфейса нет конструктора экземпляра; статический конструктор возможен, но объект не создаёт. |
| Один класс может наследовать/реализовывать несколько таких типов | − | + | У класса может быть только один непосредственный базовый класс. Одновременно реализовать несколько интерфейсов разрешено. |
| Может содержать реализацию метода по умолчанию | + | + | Абстрактный класс может содержать обычные и виртуальные методы с телом. Интерфейс может содержать реализацию по умолчанию начиная с C# 8. |
| Может объявлять свойства без реализации | + | + | Абстрактный класс может объявить абстрактное свойство, например `public abstract int HP { get; set; }`. Интерфейс может объявить контракт `int HP { get; set; }` без тела. |
| Может быть использован как тип поля или переменной | + | + | В переменной абстрактного типа можно хранить объект конкретного наследника, а в переменной интерфейсного типа — объект его реализации. Создать сам абстрактный класс или интерфейс через `new` нельзя. |
| Может наследовать классы | + | − | Абстрактный класс может наследовать другой класс, в том числе абстрактный. Интерфейс может наследовать интерфейсы, но не классы. |
| Может содержать приватные методы | + | + | У абстрактного класса могут быть приватные вспомогательные методы. Начиная с C# 8 такие методы с реализацией допустимы и внутри интерфейса. |

\* Если первая строка подразумевает именно поля экземпляра, для интерфейса ответ **−**. Поле вроде `public int hp = 100;` интерфейсу недоступно; статическое поле вроде `public static int DefaultHP = 100;` допустимо. Это не означает, что каждый реализующий класс получает собственное поле здоровья из интерфейса.

Справка по возможностям интерфейсов: [Microsoft Learn — interface](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/interface).

### Дополнительный вопрос

```text
IDamageable
    ↑ реализует
Character (абстрактный класс: Name, HP, TakeDamage)
    ├── Player : Character, IInteractable, IHealable
    ├── Enemy : Character
    └── NPC : Character, IInteractable

IInteractable: void Interact(Player player)
IHealable: void Heal(int amount)
```

У всех трёх персонажей есть имя, здоровье и получение урона. Поэтому это можно вынести в общий абстрактный класс `Character`, чтобы не копировать одинаковый код. Сам `Character` создавать не нужно, создаются его конкретные наследники.

Для диалогов нужен `IInteractable`, его реализуют `Player` и `NPC`. Лечение добавляется через `IHealable` только игроку. Враг не получает эти способности, потому что по условию они ему не нужны.

Абстрактный класс подходит, когда у родственных объектов есть общие данные и код. Интерфейс подходит для отдельной способности, которая может быть нужна разным классам. Один класс может наследовать один базовый класс и реализовать несколько интерфейсов.
